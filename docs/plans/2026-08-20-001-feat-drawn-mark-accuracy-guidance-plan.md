# feat: Accuracy guidance for drawn marks in ad-hoc themes

## Summary

Add craft guidance to the themes path so an improvised custom theme draws marks that actually read as their subject and survive a home printer. This closes the gap between what design rule 1a already specifies — *how to construct* a mark — and whether the result is recognizable. Rule 1a gains a single cross-reference line so the unthemed hand-authored line-art fallback can reach the same guidance.

## Problem Frame

The skill already specifies how to build a pictorial mark. Design rule 1a requires inline SVG with `fill="none"` and stroked paths, and the Part B self-check enforces that mechanically. Nothing specifies how to make the mark *recognizable*, and the two are independent: a mark can pass every check in Part B and still fail its job.

This surfaced concretely on a Spider-Man-themed recipe card generated by the skill. The spider emblem was fully compliant — stroked SVG, `fill="none"`, `currentColor`, print-flat — and read as a mosquito. Its legs radiated straight out of the body in smooth arcs with no joint. Redrawing them with a raised knee (hip → knee → planted foot) fixed it immediately. The difference was iconographic knowledge that the skill never captures, so the next ad-hoc theme starts from zero and re-improvises.

The ad-hoc theme checklist compounds this. Item 3 says only "invent 2-3 recurring theme-specific components," and every example it offers is typographic or geometric — a stamped badge, tilted callouts, an accent stripe, in-world labels. A theme whose identity depends on a drawn subject gets no guidance at all.

## Requirements

- R1. The ad-hoc theme path carries guidance on making a drawn mark recognizable as its subject, not merely rule-compliant.
- R2. The guidance covers print legibility for stroked marks: stroke weight relative to rendered size, spacing between adjacent strokes, and cap/join choice.
- R3. The guidance names the escape hatch — when a subject cannot be drawn recognizably in stroked line art, substitute rather than ship a bad drawing.
- R4. A saved theme spec records the marks it settled on, so a later run reproduces them rather than re-improvising.
- R5. Design rule 1a points to the guidance so the unthemed hand-authored line-art fallback reaches it.
- R6. No new reference file is created, and no verification or render-and-review step is added to the workflow.

## Key Technical Decisions

- **Guidance lands in the themes path, not inside design rule 1a.** Every Part A rule in `references/design-rules.md` is mechanically checkable by Part B, and accuracy is judgment. Putting unenforceable prose there would break that file's shape and add length to a file loaded on every single run. A one-line cross-reference buys the reach without the cost.
- **No new reference file.** The repo's stated preference — "No new reference file: each piece lands where someone already looks" (commit `689d0b5`) — and the themes README's own on-demand-loading concern both push this into files already open at the moment the guidance is needed.
- **Guidance only; no verification beat.** Explicitly declined during planning. Accuracy stays a judgment the author applies while drawing, with no added render-and-review cost per themed page. The trade-off is accepted: no mechanical check catches iconographic failure, so a weak mark can still ship.
- **Subject-agnostic guidance, not a motif catalog.** The guidance teaches how to find any subject's diagnostic features rather than shipping prebuilt drawings, so it applies to whatever a future ad-hoc theme improvises.
- **Reference consulting is an authoring-time act.** Looking at reference imagery while drawing touches nothing at render time — generated pages stay self-contained, and `custom_css` still forbids `url(`. This distinction is stated in the guidance so it is not mistaken for permission to fetch.

## Implementation Units

### U1. Drawn-mark craft guidance in the ad-hoc theme checklist

**Goal:** Give the ad-hoc path what it needs to draw a mark that reads as its subject.

**Requirements:** R1, R2, R3, R6

**Dependencies:** none

**Files:**
- `references/themes/README.md` (modify — item 3 "Signature motifs" in the Ad-hoc theme section)

**Approach:** Extend the ad-hoc checklist's item 3 material, placed per the formatting call in Open Questions. Content to cover:

- **Diagnostic features first.** Name the 2-3 traits that make the subject identifiable, and draw those before any detail. A spider is jointed legs with a raised knee plus a two-part body; a bicycle is two equal circles and a triangle frame. Miss one and no amount of detail rescues the mark.
- **Silhouette over detail.** A stroked mark has no fill and no shading, so recognition rides entirely on outline and proportion. Interior detail never fixes a wrong silhouette. The test is whether the subject is still identifiable at thumbnail size.
- **Proportion from reference, not memory.** Memory systematically distorts — legs too short, heads too small. Consulting reference imagery while authoring is fine and affects nothing at render time; the page remains self-contained.
- **Print legibility.** Stroke weight proportionate to rendered size (roughly 2–2.5 units on a 100-unit viewBox for a mark printed near 1in); uniform weight unless the theme deliberately owns the variation; round cap and join for organic subjects, miter for mechanical ones; adjacent strokes kept at least ~2× stroke width apart so ink spread does not merge them into a blob.
- **The escape hatch.** When a subject resists stroked line art — a specific likeness, a complex logo, a photorealistic scene — substitute a typographic or abstract mark instead. A bad drawing is worse than no drawing.

**Patterns to follow:** `references/themes/comic.md` section 5 "Marks and imagery" is the shipped precedent for substituting typographic marks for an icon system ("no icon system… never image assets"). Match the density and imperative voice of the existing checklist items 1-6.

**Test scenarios:** Test expectation: none — documentation change with no executable behavior.

**Verification:** The ad-hoc checklist still reads as one continuous set of instructions, and an author following it has enough to draw a subject-bearing mark without reaching for another file.

### U2. Spec template records the marks a theme settled on

**Goal:** A saved theme carries its marks forward instead of re-improvising them on the next run.

**Requirements:** R4

**Dependencies:** U1 (shares vocabulary — diagnostic features, stroke weight)

**Files:**
- `references/themes/theme-spec-template.md` (modify — "Marks and imagery" bullet in section 5)

**Approach:** The bullet today asks for `--image-filter` and any substitute the theme uses for drawn icons. Extend it so that a theme which *does* use drawn marks records, for each one, its subject, its diagnostic features, and the stroke weight and viewBox it was drawn at — enough that a later run reproduces the same mark rather than redrawing it from scratch. Keep "no icon system" as a valid and explicitly supported answer for themes that have none.

**Patterns to follow:** The existing bullet shape in section 5; `references/themes/comic.md` section 5 as the filled-in reference version of this same section.

**Test scenarios:** Test expectation: none — documentation change with no executable behavior.

**Verification:** A theme author filling out the template knows what to write for a drawn mark, and a theme with no marks is not pushed into inventing one.

### U3. Cross-reference from design rule 1a

**Goal:** The unthemed hand-authored line-art fallback can find the guidance.

**Requirements:** R5, R6

**Dependencies:** U1

**Files:**
- `references/design-rules.md` (modify — end of rule 1a)

**Approach:** Add one sentence at the end of rule 1a pointing to the themes guidance for making a mark recognizable. Call out the case that matters most: hand-authored art on coloring, image, and drawing-prompt pages when no image backend is available, where the drawing *is* the deliverable rather than decoration. Keep this strictly a pointer — no craft content enters this file, preserving the property that every Part A rule maps to a mechanical Part B check.

**Patterns to follow:** Rule 1a's existing cross-reference style (it already refers outward to the self-check).

**Test scenarios:** Test expectation: none — documentation change with no executable behavior.

**Verification:** Rule 1a gains no unenforceable content of its own, and a reader hitting the hand-authored-SVG fallback is one hop from the guidance.

## Scope Boundaries

**Not doing:**
- A Spider-Man theme spec, or any named-character theme
- A library of prebuilt motif SVGs shipped with the skill
- Vendored SVG assets committed to `assets/`
- Any render-time fetching — generated pages stay self-contained
- A verification, render, or review step in the workflow
- Changes to the Part B self-check

**Deferred to follow-up work:**
- Measuring whether this guidance actually improves output. The A/B eval harness under `eval/` exists to answer exactly this question for skill edits (see `docs/plans/2026-08-19-001-feat-print-skill-ab-eval-harness-plan.md`); running this change through it is worthwhile once that harness lands, but is not a prerequisite here.

## Open Questions

- Whether the guidance sits inline within checklist item 3 or as a short subsection directly beneath the numbered list. Decide while writing based on length — if it runs past roughly eight lines, a subsection keeps the checklist scannable. This is a formatting call with no downstream consequence.
